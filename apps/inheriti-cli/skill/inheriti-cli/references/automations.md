# Business automation lifecycle

Check that the installed build exposes automation commands. Establish the selected Business Organisation, identify the plan with `plans list`/`show`, and inspect `automations list` plus `automations grants PLAN_ID` before creating anything. Reuse an existing connection when its provider, workload identity, environment, and trust match; do not create a duplicate. A manager creates or changes the connection; a plan editor grants access. Business checks both permissions.

The order is: existing workload and CLI runtime → connection (`automations create`) → identity pairing or verification (`automations pair ...` or `automations verify`) → plan grant (`automations grant create`, then `activate`) → mapping and runtime setup (`automations setup` or `automations usage`) → run and inspect safe plan/member logs. `automations trust` changes the non-secret identity policy and may require reverification; `automations disable` stops a connection. `automations grant member` changes its responsible member; `revoke` ends a grant. Present the exact connection, plan, member, and effect before these changes. Never pass a workload proof, private key, or credential as an argument or through chat.

`automations pair start [--connection ID]` opens a ten-minute window; `pair redeem` runs inside the configured workload and sends a fresh native proof directly to Business. Provider helpers can pair a temporary ECS task, Cloud Run job, or SSM-managed EC2 instance after target/revision inspection and confirmation. `automations verify` opens a native proof-entry window only when there is already a secure transfer route; it does not fetch proof from Cloud Run or ECS. Review the provider-specific route in [provider workflows](automation-providers.md).

`automations setup --plan PLAN_ID --connection CONNECTION_ID ...` maps plan fields to runtime inputs. Use `--map-all` with optional `--except`, repeatable `--only`, or `--map NAME=ASSET.FIELD`; inspect the complete mapping before action. It can print or save a launcher for a custom/container runner, preview a managed ECS/Cloud Run change, or prepare an EC2 launcher and systemd unit. Cloud changes require an explicit `--apply` with a prepared image and reviewed target revision; EC2 writes require `--install` and confirmation. The CLI does not invent or create an app, repository, workload, IAM role, or cloud account. `automations usage` generates a GitHub workflow only for a verified connection, active grant, and Business-verified Action/CLI release.

For an application that already reads a provider secret store, `secrets publish aws|google` previews exact field-to-destination mappings and applies only with `--apply`. This is a **one-time copy**: later plan edits or revocation do not rotate or delete the provider copy. Prefer direct `secrets exec --automation` inside a verified workload when ongoing plan control is intended. Check `inheriti help secrets publish aws|google` for current target flags; never put values in them.

# Inheriti MCP

Inheriti MCP connects Inheriti Business to MCP-compatible clients over stdio. The MCP client starts the server; running `node dist/main.js` directly in a terminal waits for MCP messages.

Downloading the `.tgz` package does not install the `inheriti-mcp` command. In PowerShell, from the download folder, run `npm.cmd install --global ".\safetech-inheriti-mcp-<version>.tgz"`. Verify it with `inheriti-mcp --version` and `where.exe inheriti-mcp`.

Call `list_organizations` to open browser sign-in and see the available organizations, then `select_organization` if needed. If the browser does not open, use the URL returned by the tool. `list_backup_plans` shows plan metadata. `create_plan_with_assistant` opens a native window for local asset suggestions and review; use its job ID with `check_plan_creation_status`.

## Automation setup

Automation setup is available when this MCP server targets a local Business API (`localhost`, `127.0.0.1`, or `*.localhost`) or the exact Business dev API (`https://business-api-dev.inheriti.com/integrations/`). It remains unavailable for stg and prod. Sign in through `list_organizations` and select the intended organization first. The Business API controls access: listing connections requires tenant settings permission, and listing a plan's grants requires permission to edit that plan.

1. Call `list_automation_connections` for safe connection metadata. Call `list_automation_grants` with a `planId` to inspect that plan's grants. `list_automation_members` provides member IDs, display names, and status to choose the responsible member; it omits email addresses.

Use `list_member_logs` with a `memberId` to read the authorized Business activity stream. Optional `source` (`MEMBER` or `AUTOMATION`), `from`, `to`, `limit`, and `offset` filters match the Business log view. The tool returns safe event fields without raw event data.
2. Use `create_automation_connection` or `change_automation_trust` with nonsecret provider trust details the human has supplied. Never pass a private key, credential, or identity proof in tool arguments or conversation text. Use `disable_automation_connection` when access should end.

   For GitHub, ask for the repository, environment, and full `workflow_ref` claim. For Google Cloud or AWS, ask for the existing Cloud Run job or ECS service target, then call `inspect_automation_cloud_identity` to obtain its service account numeric ID or task role ARN using the locally authenticated provider CLI. Ask for a Google audience base; MCP appends the connection ID and returns the exact expected audience. For Portable, ask for the runner's PEM public key and key ID; the private key stays on the runner. GitHub creation and trust changes also return the exact expected audience.
3. Call `start_automation_setup` with the connection ID to open the native window for human identity proof. For a pending connection, use its ID from `list_automation_connections` to resume verification. Poll `check_automation_setup_status` until `COMPLETE`, `FAILED`, or `CANCELED`; pass `cancel: true` to stop a waiting job. Organization switching and logout also cancel it.
4. Use `create_automation_grant` with the plan, connection, and responsible member IDs, then `activate_automation_grant` after review. `replace_automation_responsible_member` and `revoke_automation_grant` manage an existing grant. Business enforces plan editor permissions. Re-list metadata to see the current state.
5. For GitHub, call `get_backup_plan` and offer the actual `asset.code.fieldName` choices in its safe metadata. After the human selects one, call `github_automation_usage` with that nonsecret selector, the plan ID, and verified connection ID; never request a field value. The tool returns copyable YAML and the exact repository, `.github/workflows/…` file, and branch required by the verified connection. It fails if the grant is inactive, the connection is unverified, its workflow reference is invalid, or Business has no verified Action and CLI release. Do not substitute `@main`, a guessed SHA, or npm `latest`.
6. For Cloud Run jobs or services, AWS ECS, a VM, a Kubernetes workload, or a custom runner, ask which plan text fields the application needs. Call `prepare_automation_runtime` with `mapAll: true` for all text fields, `mapAll: true` plus `exceptFields: ["ASSET.FIELD"]` to omit some, or `onlyFields: ["ASSET.FIELD", ...]` to select a few. Use `mappings: [{selector, envName}, ...]` to rename generated environment variables or map fields explicitly; the older `field` and `environmentVariable` inputs still work for one field. Show the returned selector-to-environment mappings to the operator. For managed Cloud Run or ECS updates, also ask for the existing target and the absolute CLI path inside its image. Omit the target for a VM or Kubernetes workload to receive a launcher for the operator to install; MCP does not change that server or cluster. The tool checks the verified connection and active grant; managed targets receive an inspected preview and current revision, while manual targets receive only a launcher. Ask the operator to publish an immutable image containing the released CLI. After the operator reviews the exact mappings and preview and authorizes the provider change, call `apply_automation_runtime` with the reviewed explicit `mappings`, image digest, and exact expected revision. The apply tool deliberately has no bulk selector: a field added to the plan after review cannot enter the deployment silently. It uses the authenticated local provider CLI to update the Cloud Run job or service or ECS service and returns only safe revision metadata. The tool cannot build an arbitrary application image or schedule a job. Keep existing environment values and application arguments out of tool responses and conversation text.

The list tools return only allowlisted metadata, and setup status contains no proof or credentials. A connection appearing in a list does not establish that a provider workload can use it. The [CLI setup workflow](../../integrations/README.md#automation-setup) also reserves its window for identity proof.

`reveal_plan_secret`, `download_plan_asset`, and `check_reveal_status` are available by default. Reveal opens a native window after authorization. MCP tool responses do not contain protected values. Existing configurations with `--enable-secure-delivery` continue to work. This app is part of [Inheriti Integrations](../../README.md).

For direct runtime access, use the Inheriti launcher from `prepare_automation_runtime` and `apply_automation_runtime`, which runs `inheriti secrets exec`. Cloud-store publication is an optional one-time copy for existing consumers. Subsequent reads of a published copy use provider IAM; plan changes or revocation do not update or delete it, and there is no automatic synchronization or rotation.

`publish_plan_fields_to_aws` previews or publishes explicit `selector` to `key` mappings. Supply `planId`, AWS `region`, `expectedAccountId`, and exactly one destination: `secretName` for one Secrets Manager JSON secret, or `parameterPrefix` for individual SSM SecureString parameters. Preview with `apply: false` to inspect target metadata. Get the user's approval for the exact destination and mappings before `apply: true`. If custody requires the native window, it displays the destination and mappings. Poll `check_reveal_status` for the publication result. Protected values stay out of MCP responses. The [CLI publication guide](../inheriti-cli/docs/automation-setup.md#publish-plan-fields-to-aws-secrets) lists AWS permissions and update limits shared by this tool.

`publish_plan_fields_to_google_cloud` previews or publishes explicit `selector` to `key` mappings as separate Google Cloud Secret Manager secrets. Supply `planId`, `projectId`, `secretPrefix`, and mappings. Preview with `apply: false`; ask for approval of the exact project, secret names, and fields before `apply: true`. Apply uses the same protected reveal flow and returns no secret values. Poll `check_reveal_status` when a native custody window is required. The [Google Cloud publication guide](../inheriti-cli/docs/automation-setup.md#publish-plan-fields-to-google-cloud-secret-manager) explains credentials and update limits.
